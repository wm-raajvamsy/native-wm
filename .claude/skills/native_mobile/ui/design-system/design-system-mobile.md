# WaveMaker Mobile Design System (Global Tokens)

A design system is coherent when the **brand foundation lives in one place**. Set `color.primary.@` once and every button, label, link, and card that references `{color.primary.@.value}` updates app-wide. This skill authors that global layer: brand colors, semantic colors, surfaces/neutrals, typography, spacing, radius, and elevation — for **light and dark** themes — and then makes sure components inherit it instead of hardcoding values.

This is the **top-down** skill. The existing `figma-to-design-tokens-mobile` skill is **bottom-up** — it mints per-component appearances from a specific design. They compose: establish the system here, then author component appearances there (which already enforces global-token-first).

**Read `global-token-schema` before writing any file** — it is the single source of truth for the override file paths, the value-only sparse-override leaf shape, the `@`-anchor rule, per-category structure templates, the derived-color formula table, AND the slot-selection + blast-radius guide (what each token affects and which scale step a measured value belongs in).

## Two ways this skill runs

1. **Standalone (top-down)** — the user explicitly wants to create/customize the design system, set up a theme, apply brand colors app-wide, or rebrand. Run the full workflow below.
2. **Delegated global-authoring step inside a page build** — `screenshot-to-wavemaker-mobile` / `figma-to-wavemaker-mobile` invoke this from their **STEP 0 (Part B — brand posture)** whenever the design plan resolves to *establish* or *mutate* globals, to lift the brand palette AND the measured design language (density, roundness, type, weight) into the global layer *before* component tokens are authored in STEP 3. In this mode: take what the caller measured (or **ask the user** — Phase 1), write the global overrides (Phases 3–4), hand off any component-specific dimensions (Phase 5), **notify the user** (Phase 6), then return so the caller's STEP 3 component generation references the new globals. Skip Phase 5's component *spot-check* — the caller owns component authoring.

## Workflow

### Phase 1: Capture the design language

Build a complete picture before writing anything. The design language has two halves — **color** (the palette) and **layout** (density, roundness, type, weight). Extract BOTH; layout is not an afterthought.

**Sources** (combine whatever the user provides):

- **User-provided values** — brand hexes, font family, density/radius preference, "make it dark". Authoritative.
- **Reference screenshot** — an **app UI screenshot** (infer the system from the rendered design) or a **design-system / style-guide screenshot** (read swatches, the type ramp, spacing/radius samples directly). Sample exact values; don't approximate to foundation defaults.

**Color extraction.** Sample the palette to the 9 seeds: the accent on the **primary CTA + logo** → `primary` (when two chromatic accents compete, the action/logo color wins — a large hero/background field is NOT automatically primary); a clear second accent → `secondary`/`tertiary`; status colors → `success`/`warning`/`error`/`info`; page/card backgrounds and body text → `background`/`surface`/`on-surface` (use the representative **solid** app surface — a login/onboarding hero or a gradient is page-level, not the global `background.@`). Sample **only** these seeds — the companions (`on-*`, `container`, `fixed`, surface tiers) are regenerated by studio from the seeds (Phase 4), so don't sample or author them. Studio re-derives every `on-*` by its binary contrast formula, so an on-color the design happens to show (e.g. white text on a colored button) won't be preserved if it disagrees with the formula.

- **Monochrome gate:** a brand exists only if there is a CHROMATIC accent. If the reference is **monochrome/grayscale** (only black/white/grays — whether a lo-fi wireframe or a polished real UI; **color content decides this, NOT fidelity**), or there is no reference and no user hexes, **STOP and ASK** for the primary brand color before authoring. A monochrome design is brand-LESS — do NOT treat black as `primary` or gray as a brand surface, and do NOT invent a brand unprompted. If the user declines, keep the foundation defaults (never black-as-brand) and state the assumption.

**Layout / design language — measure, then quantize to the scale.** Reference frame: 375px viewport, ~343px content width. Screenshot measurements are approximate → **snap each to the nearest scale step; never invent an exact-px scale.** For each category, decide the delta from the foundation default and note its blast radius from `global-token-schema` (slot-selection + blast-radius guide):

| Category | Measure | Quantize to (file) |
|----------|---------|--------------------|
| Spacing / density | dominant repeated paddings & gaps (card padding, section gaps, row spacing) vs the 4px rhythm | rescale `space.1`–`space.4` down (tight) / up (airy); **keep `space.0`=0** (`space.json`) |
| Roundness | corner radius of cards / buttons / inputs / images | sharp ≤2px → keep/`none`; 4–8px → `xs`/`sm`; 10–16px → raise `sm`/`md`/`lg`; fully round → components use `pill`/`circle` (keep those at 1000px) (`radius.json`) |
| Typography | font family; body size; heading sizes; label/button text size; weights; line-heights | `font.family.brand`/`plain`; `body.*`, `label.*`, `h1`–`h6` (ramp keys TOP-LEVEL) (`font.json`) |
| Border | line weight (hairline 1px vs 1.5–2px) & style | `border.width.base`/`1`; `border.style.base` (`border.json` / `border-style.json`) |
| Elevation | flat vs shadowed cards | `elevation.shadow.1` lower/raise, or `none`; tint via `color.shadow.@` (`elevation.json`) |
| Icon size | icons notably larger/smaller than 24px | `icon.size.@`/`md` (`icon.json`) |
| Component dims | per-widget sizes that differ (navbar/input height, toggle, rating star) | NOT global — hand off to the component layer (Phase 5) |

**ASK gate for the design language.** If there IS a screenshot/design → **measure** (don't ask). If there is **no** visual source and the user hasn't specified → **ASK** for density (tight/default/airy), corner personality (sharp/rounded/pill), and font before authoring. If they decline, keep the foundation defaults and state the assumption — do NOT silently ship foundation defaults as if they matched a design.

**Fallback (after asking).** If the user gives only partial direction, derive a coherent system from the foundation defaults nudged by whatever hints exist; choose consistent values and note the assumptions. Don't block indefinitely.

**Dark theme:** author the inverted palette (Phase 4) whenever dark mode is in scope.

### Phase 2: Preflight — inventory existing global overrides

Before writing, see what's already there so you **extend** the system instead of clobbering it (and to converge a multi-page app onto one vocabulary):

1. `~{find_files_by_glob}` with pattern `**/*.json` on folder `src/main/webapp/design-tokens/overrides/global`.
2. Batch every returned path into a SINGLE `~{read_files}` call; parse each into `category → { tokenPath → value }`.
3. If the folder is absent/empty, treat it as a fresh system.

> **⚠️ Read before you write (state-aware file tools).** A brand-new file can go straight to `~{write_file}`. If a target file already exists, you MUST `~{read_files}` that exact path FIRST, then `~{edit_file_content}` to merge your changes into it — overwriting an existing file without a prior read in this turn is rejected.

### Phase 3: Author the global override files

Write to `src/main/webapp/design-tokens/overrides/global/<category>/<file>.json`, following `global-token-schema` exactly. Core rules (full detail in the reference):

- **Value-only, sparse leaves**: `{ "value": "<non-empty string>" }`. No `type`/`attributes`. Author ONLY the leaves you change. Numbers (weights) are strings.
- **Mirror foundation nesting**, rooted at the category key.
- **Colors — one object per token, `@` on every shade.** Merge every shade of a color (`@`, `container`, `fixed`, …) into a SINGLE parent object; never write the same key (`primary`, `on-surface`, `outline`, …) twice — `JSON.parse` keeps only the last and silently drops the rest, and the validator won't catch it. Every color leaf ends in `@` except `color.outline.variant`. After writing, re-read each color file to confirm no key repeats. (Full shape + self-check: `global-token-schema` → Color.)
- **References must resolve** (`{token.path.value}`).
- **Leverage existing tokens by default**: reuse and override existing foundation slots — do NOT mint new global tokens on your own (a "brand accent" is usually `tertiary`; a custom gap is a `space.*` step). Add a brand-new custom token ONLY when the user **explicitly asks** for additional/custom tokens. When you do, follow `global-token-schema` → "Adding custom global tokens": namespace it cleanly, author light + dark for colors, and **pair it with the component appearance that references it** (delegate that to `figma-to-design-tokens-mobile`) — an unreferenced custom global token has no effect.

Files to write, in order:

1. `global/color/color.light.json` — the seed palette (light).
2. `global/color/color.dark.json` — same paths, dark palette (Phase 4).
3. `global/font/font.json` — `font.family.*`, any `font.weight` additions, and top-level ramp deltas (`body`, `h1`–`h6`, `label`, `p`). Ramp keys are **top-level**, not under `font`.
4. **Every layout category your Phase 1 measurement flagged as a delta** — `global/space/space.json` (density), `global/radius/radius.json` (roundness), `global/border/border.json` + `global/border-style/border-style.json` (weight/style), `global/elevation/elevation.json` (depth), `global/icon/icon.json` (icon size), `global/opacity/opacity.json`.

Skip only a category the design genuinely leaves at the foundation default — a no-op file is noise. But if the design is denser / rounder / differently-typed than the foundation, NOT authoring `space` / `radius` / `font` is the exact bug this skill exists to prevent: the app silently inherits the 4px rhythm, 8px radius, and Roboto defaults, and the screenshot's feel never lands.

### Phase 4: Seeds only — studio regenerates the companions

Author only the 9 seeds. The companions (`on-*`, `container`, `fixed`, surface tiers) are **formula-derived, and studio's `setDesignTokensTool` regenerates them from the seeds** whenever the seeds change — so do NOT hand-author them. A companion leaf you write yourself is redundant, and when it diverges from the formula it gets silently overwritten by studio's regeneration. The seeds are the durable input; keep the override files to the seeds.

Author `color.light.json` and `color.dark.json` with the seeds only, in **both** themes:

- **Light** — the seeds sampled in Phase 1.
- **Dark** — the inverted-brightness seeds (brand *lighter*, `background`/`surface` near-black), authored at **parity** with light (same seed paths). Dark seeds are authored, not derived; studio then regenerates dark's companions from them.

**The companion formula** (full table in `global-token-schema`):

- **`on-*` is binary** — `#FFFFFF` if `contrast(seed, #FFFFFF) > 4.5` else `#000000`, never a mid-tone.
- `container` = `lighten(40%)`, `fixed` = `lighten(45%)`, `on-*.container` = `darken(20%)`; surface tiers from `surface` (`variant` +6%, `dim`/`tint` −10%); `on-surface` = lighten(70%) of surface; `on-background` = darken(80%) of background.

By default this table is **reference only** — use it to preview what studio will generate and sanity-check a seed for contrast; if it would produce an illegible or off-brand companion, fix the **seed**, not the companion.

**Generate the companions only when the user explicitly asks** for them (e.g. to lock a specific `on-primary` studio's binary formula won't pick). Then author those leaves by **replicating the formula above** — in both `color.light.json` and `color.dark.json`, keeping the binary `on-*` rule — and note that studio's regeneration may re-derive them from the seeds unless it's told to preserve them.

### Phase 5: Bridge to components

The global layer only shows up if components reference it — and some layout the screenshot dictates lives ONLY at the component layer.

- **Reference, don't hardcode**: component appearances MUST reference global tokens (`{color.primary.@.value}`, `{body.large.font-size.value}`, `{radius.sm.value}`, …) — never a brand hex or a px that duplicates a global token. (See `styling-system` / `foundation-tokens`.)
- **Hand off component-specific dimensions.** Fixed per-widget sizes are hardcoded literals in the foundation — no global token reaches them (navbar height, input height, toggle size, rating star size, slider/carousel/video heights; see `global-token-schema` → *Dimensions that are NOT global tokens*). Where your Phase 1 measurement shows a widget's dimension differs from the default, pass it to `figma-to-design-tokens-mobile` to set at the component-override layer, referencing a global scale step where the value matches one.
- **Delegate** per-component appearance authoring to `figma-to-design-tokens-mobile` — it enforces global-token-first and the existing-override reuse pass. This skill does not author `appearances`.
- **Spot-check** the existing `design-tokens/overrides/components/**` files (Phase 2 inventory): where a component hardcodes a hex that now equals a brand/semantic global, flag it to be replaced with the reference. Don't silently rewrite unrelated component styling.

### Phase 6: Notify the user (always)

A global change is high-impact yet nearly invisible in the file tree — **tell the user what changed and how far it reaches.** After writing (or deciding nothing needed to change), surface a concise summary:

- The **palette** detected/supplied (primary/secondary/accent + key surfaces) with hexes, and the **design-language deltas** (density, roundness, font, borders, elevation).
- The **global tokens set** — name the files (`color.light.json`/`color.dark.json`, plus any `space`/`radius`/`font`/`border`/`elevation`/`icon`) and confirm the **seeds** were authored in **both** themes (studio regenerates the companions from them).
- The **blast radius**, from `global-token-schema` — e.g. "tightened the `space` scale → padding/gaps across ~27 components"; "raised `radius.sm`/`md` → cards, buttons, inputs, chips"; "`primary` → filled buttons, links, active states, progress, tabbar".
- The **layer bound**: global tokens set the app-wide design language; component-specific dimensions were set at the component layer; the page's arrangement/structure comes from the markup — tokens do NOT reproduce pixel-exact layout.
- Any **assumptions** (e.g. "you gave only a primary; studio will regenerate the companions from it, and I assumed rounded, standard-density — say the word to adjust").

Example:

> Applied to the global theme: `primary` `#0E7A5F` (emerald — studio will regenerate `on-primary`=white + a tinted `container` from this seed), `secondary` `#F2A516`; **denser** spacing (`space` scale ≈−25%, affects ~27 components' padding/gaps) and **rounded** corners (`radius.sm`/`md` raised → cards, buttons, inputs, chips) — light **and** dark. Every component referencing these inherits it; widget-specific sizes (navbar/input height) I set at the component layer; page structure comes from the markup.

When delegated from a page build, keep it to one or two lines and continue — don't stop the build.

## Verification checklist

Before finishing, verify EVERY item:

- [ ] Files are under `src/main/webapp/design-tokens/overrides/global/<category>/<file>.json`; color uses `color.light.json` + `color.dark.json`; other categories are single mode-less files.
- [ ] Every override leaf is `{ "value": "<non-empty string>" }` — no `type`, no `attributes`, no `derivedFrom`/`formula`. Weights/numbers are strings.
- [ ] Sparse: only changed leaves are present; no full foundation tree copied; no no-op files.
- [ ] Color files pass the shape self-check: every color token is ONE object (no key repeated at any level — re-read to confirm) and every color leaf ends in `@` except `color.outline.variant`. (The validator catches neither slip.)
- [ ] **Seeds only by default** — no hand-authored companions (`on-*`/`container`/`fixed`/surface tiers); studio's `setDesignTokensTool` regenerates them from the seeds. Author companions ONLY if the user explicitly asked, and then by replicating the formula in both themes (binary `on-*`).
- [ ] **Layout deltas measured from the design were authored** (`space`/`radius`/`font`/`border`/`elevation`/`icon` as applicable) — density/roundness/type is NOT silently left at foundation defaults. `space.0` kept at 0; radius uses named steps.
- [ ] Every `{...}` reference resolves to a real token. Existing foundation slots reused/overridden by default; custom tokens added ONLY if the user asked — and each custom token is referenced by a component appearance.
- [ ] Typography ramp keys (`body`, `h1`–`h6`, `label`, `p`, `display`) are TOP-LEVEL in `font.json`; only `font.weight`/`font.family` nest under `font`.
- [ ] Light/dark parity: same paths on both, inverted brightness, binary `on-*` contrast.
- [ ] Components reference globals (no duplicate hardcoded brand hexes); component-appearance work — and any component-specific dimensions the design dictates (navbar/input/toggle/rating sizes) — delegated to `figma-to-design-tokens-mobile`.
- [ ] User was notified (Phase 6): palette + design-language deltas, the tokens/files set (light & dark), the blast radius, the layer bound, and any assumptions.

## Quick reference: common mistakes

| Wrong | Right | Why |
|-------|-------|-----|
| Writing `type`/`attributes` on override leaves | `{ "value": "..." }` | Overrides are value-only |
| `"primary": { "value": "#..." }` | `"primary": { "@": { "value": "#..." } }` | Colors nest under `@` |
| `color.json` | `color.light.json` / `color.dark.json` | Theme suffix required for color |
| Hand-authoring `on-primary.@` / `primary.container.@` companions unprompted | author only the seed `primary.@` (generate companions only if the user asks) | Studio regenerates companions from the seeds — hand-authored leaves get overwritten |
| Leaving `space`/`radius`/`font` at defaults when the design is denser/rounder/differently-typed | author the measured deltas | Otherwise the app inherits the 4px/8px/Roboto foundation feel — the layout never matches |
| Rescaling `space.0` | keep `space.0` = 0 | It's an explicit zero (flush edges); rescaling injects unwanted space |
| `"font": { "body": { "large": {...} } }` | top-level `"body": { "large": {...} }` | Ramp keys are top-level |
| `"font-weight": { "value": 600 }` | `"value": "600"` | `value` must be a string |
| Minting `color.brand.@` unprompted | reuse/override an existing foundation slot | Leverage existing first; add custom tokens only when the user asks, then reference them |
| Hardcoding the brand hex in a button appearance | `{color.primary.@.value}` | Components must reference the system |
